# 舌战非教程双队回合开始组合核 v1

日期：2026-10-22。实现：[debate-turn-start.ts](../../packages/engine/src/debate-turn-start.ts) · [API 与精确 DTO](../engine/debate-turn-start-v1.md) · [固定来源与完整政策](../sources/debate-turn-start-v1.json) · [手工场景](../../data/scenarios/debate-turn-start-example-v1.json)。

`evaluateDebateTurnStart` 使用独立 profile `debate-turn-start-reference-v1`，只组合固定现代参考中**非教程、两队的 TurnStart**：按队0完整处理后再处理队1，重置已出牌、条件恢复再考额度、复用既有补牌核、按最终有效手牌判断正计时刚胆是否退怒，最后清除崩坏标记。它不是完整回合或会话，不执行 TurnEnd、计时递减或牌组再生成。

每队显式给出七个物理槽、有效容量、完整18项当前牌组及游标，另给本队需要的0或1份话题修补抽样。整个双队调用为纯函数事务：成功同时返回两队与完整审计，任一队失败则不公开任何部分状态，也不修改调用者的数据。

## 2. 显式双队检查点

完整输入字段为 `schemaVersion`、`profile`、`policies`、`isTutorial` 与 `characters`：

| 字段 | 准入要求 |
| --- | --- |
| `schemaVersion` | 严格为1 |
| `profile` | `debate-turn-start-reference-v1` |
| `policies` | 与完整 `DEBATE_TURN_START_POLICY_V1` 相同；仅政策id不足 |
| `isTutorial` | 必须为布尔false；true是 `unsupported-tutorial`，不是跳过补牌后继续 |
| `characters` | 恰好两份稠密记录；数组下标0和1分别为来源队0与队1 |

每份角色输入必须完整提供：

| 字段 | 准入要求 |
| --- | --- |
| `personality` | 已解析的 `timid`、`calm`、`bold` 或 `reckless` |
| `angerTimer` | 整数0..4 |
| `maxCardCount` | 整数4..7，包含保留0槽 |
| `hand` | 恰好七个物理槽，详细分域见下一节 |
| `playedCard` | 整数−1..14；本次成功时无条件写为−1 |
| `canRethink` | 布尔值，进入本次回合开始前的再考额度 |
| `crumbled` | 布尔值，进入本次回合开始前的崩坏标记 |
| `cardTape` | 恰好18个整数牌码1..14，表示本队完整当前牌组 |
| `deckCursor` | 整数0..18，本次取牌的起始游标 |
| `rawDraws` | 本队0或1份既有补牌核格式的话题修补记录 |

合法修补记录为 `{"role":"debate-fill-topic-repair","bound":9,"value":0}`，其中value可以是0..8任一整数；不接受种子、回调、布尔值或其他抽样角色。`rawDraws` 字段不能省略，即使该队不需要修补，也必须明确给 `[]`。是否必须消费一份由实际补牌后的修补条件决定，不能仅凭该队是刚胆或冷静预先认定。

两队的完整字段和每份已提供draw的role、bound、value域先全部检查，然后才处理队0。只有“本队实际是否需要这份合法draw”的判断交由原补牌核在修补阶段完成。例如队1提供错bound会在组合求值前拒绝；队1提供合法但不需要的draw则在该队补牌阶段拒绝，两者都不公开队0部分结果。

两队有**独立的当前牌组、游标和修补数组**，没有共享游标或隐含未来发牌流。完整18项都需满足牌码域，包括游标之前、此次不会取到的牌。给定牌组不认证来源生成程序、分布或可达性；给定容量和性格不认证人物、智力、覆盖值、书籍或物品配置已正确解析。

这里的0..4计时、4..7容量和−1..14已出牌是工程准入边界。来源判断 `angerTimer>0` 不意味着本接口可以接纳任意正整数；timer5、cap8或越界牌码不能通过静默clamp变成支持值。

## 3. 七物理槽不等于有效手牌长度

令本队有效容量为 `maxCardCount`：

1. 物理0槽允许输入−1..14任一整数，包括现有普通牌或话术。进入补牌时无条件覆写为再考0，不取牌、不推进游标，也不消费修补抽样。
2. 有效可出牌槽为物理1至 `maxCardCount-1`，每槽只允许−1或1..14。−1是待补空槽；有效可出区中的0必须拒绝，不能当作额外保留牌或空位。
3. 物理 `maxCardCount` 至6是非激活尾槽，每槽允许−1..14，包括0和普通牌。它们不参与填牌、修补、排序或刚胆普通牌计数，按原物理位置原值保留。
4. `hand.length` 总是7，即使有效容量只有4。只有4项的数组不是合法七槽输入，不能替调用者补尾槽。

**先保留空洞的原位置，再补牌，不先压紧。** 例如有效可出区 `[-1,11,-1,13]` 的新增目标依次是物理1与3，不是先把11和13挪到前面再填物理3与4。最后新增原槽决定可能修补的位置，压紧会改变来源规则及审计。

成功时只把补牌核的已排序有效前缀写回七槽副本，非激活尾槽保持不动。容量4且尾槽有普通牌9的满话术刚胆，仍会因为**有效前缀**没有普通牌而退怒；不能把七个物理槽全部纳入统计。

## 4. 来源逐队顺序

所有调用者数据先安全分离并检查公开合同，再在独立候选数据上求值。完整队0处理结束后才处理队1，而不是先重置两队已出牌、再恢复两队额度、再一起补牌。

每队的顺序是：

1. `playedCard=-1`，不因原值已经是−1而跳过该规则。
2. 若进入本队时 `crumbled=true`，将 `canRethink` 置true。
3. 若 `angerTimer>0` 且 `personality='calm'`，再将 `canRethink` 置true。否则不修改额度；不能在未触发恢复时默认写false。
4. 非教程限定下调用既有补牌核，恢复0槽、补满有效空位、按需话题修补、排序，并更新本队游标。
5. 若 `angerTimer>0` 且 `personality='bold'`，统计**补牌、可选修补和排序全部完成后的有效手牌**内牌码1..9的数量；只有数量为0时才把timer写0。其他情况保留进入本队时的timer。
6. `crumbled=false`，至此才结束本队处理并转入下一队。

恢复额度的等价结果为：旧额度 OR 旧崩坏 OR（正timer且冷静）。这是本局部结果的逻辑概括，不授权把来源审计重排为跨队批量处理。

| 旧额度 | 旧崩坏 | 正timer且冷静 | 最终额度 |
| --- | --- | --- | --- |
| false | false | false | false |
| true | false | false | true，保留旧值 |
| 任意 | true | 任意 | true |
| 任意 | false | true | true |

崩坏为真与正timer冷静可以同时成立；两项都属于来源恢复条件。timer0的冷静不会仅因性格恢复额度，但仍可以通过旧崩坏恢复。正timer刚胆、胆小或莽撞本身不恢复额度。刚胆退怒只写timer，不撤销先前已经恢复的再考额度。

这里没有计时递减。正timer且仍持有普通牌的刚胆保留原timer；非刚胆也保留原timer，不把3变2或把1变0。清除崩坏标记不重新计算崩坏层，不触发HP、压力、胜负或其他阶段。

## 5. 复用原补牌核，不复制第二套算法

组合层直接调用既有 [evaluateDebateHandFill](../../packages/engine/src/debate-hand-fill.ts)，沿用其完整政策与成功收据。该依赖核及其完成辅助核保持不变；组合层只负责七槽适配、回合开始前后状态与双队顺序。

适配时把有效物理1至末槽的−1逐个映射为补牌核的 `null`，其他有效牌码原样传入，既不丢掉空洞，也不包含0槽和非激活尾槽。补牌核的 `preSortSlot` 因而仍对应本次输入的原始有效物理槽。

既有补牌规则为：

- 先恢复0槽，再按有效空位原槽升序从本队当前牌组取牌，每个空位推进一次游标。
- 所有空位都填完后统计普通牌。若数量为0且本次至少新增过一槽，消费唯一修补记录，将**最后新增原槽**替换为 `1+value`。
- 修补不是额外取一张牌，不再推进游标；被修补的牌仍保留其原先 `tapeIndex` 与被覆盖牌码的审计。
- 整个有效前缀按牌码数值升序排序，包括保留0；非激活尾槽不参与。
- 填后已有普通牌不修补；满手全话术且没有新增槽也不修补。后者不是输入失败。

数值排序中的同值身份按原槽升序追踪，只是既有核的确定性工程审计策略，不证明来源 `Array.Sort` 稳定，也不生成跨回合、跨会话永久token。组合层不能把该审计提升为原生物理牌身份。

### 5.1 刚胆必须重新看最终有效手牌

既有补牌收据中的 `topicCardCountAfterFill` 是**普通填牌后、可选话题修补前**的数量，不是 TurnStart 应使用的最终计数。组合层必须统计补牌返回的最终有效手牌，不能直接把该收据字段当作退怒依据。

必须区分两种正timer刚胆：

| 情形 | 补牌核动作 | 修补前普通牌数 | 最终普通牌数 | TurnStart结果 |
| --- | --- | --- | --- | --- |
| 原可出区已满且全是话术 | 不取牌；无新增槽，所以不修补 | 0 | 0 | timer置0 |
| 有空位，全部填入话术且仍无普通牌 | 修补最后新增原槽为1..9 | 0 | 1 | 保留正timer |

第二行缺少所需抽样时整个双队事务失败，不产生“刚胆退怒但补牌失败”的折中结果。保留普通牌或新取普通牌也会使最终计数为正，不需要修补且不退怒。0槽的再考0与尾槽普通牌都不能增加刚胆计数。

## 6. 当前18牌边界与抽样顺序

本版本每队只支持已提供的一个完整18项当前牌组，不调用再生成、不回绕、不扩展牌带，也不借用另一队的牌组。

- `deckCursor=18` 本身合法：若有效可出区没有空位，则不需要新牌，可以成功。
- 从游标17补恰好一个空位，可以成功并返回游标18。
- 若仍有空位却需要第19项，返回 `unsupported-deck-regeneration`。即使已在内部补过别的槽，仍不公开部分手牌或部分游标。
- 一次话题修补不能替代缺失的牌组项；必须先有足够牌填满全部有效空位，才能进入修补判断。
- 队1失败会拒绝整个调用，即使队0在私有候选中已完成恢复、补牌、修补与退怒检查。

每队恰在修补条件成立时消费1份 `debate-fill-topic-repair`，否则消费0份且必须没有额外记录。缺失、语义不合法或多余记录不静默修正。本队记录最多1份，两队合计最多2份。已提供记录不是已消费记录；成功收据中的实际消费顺序才表示本次采用的提供值。

全局审计顺序遵循队0后队1，各队保留自己的补牌完整嵌套收据和局部索引。若只有队1修补，全局第一份消费属于队1；不能为了凑队0位置插入虚假抽样。两队都有修补时，先队0唯一记录，再队1唯一记录。

本核没有外部RNG调用。bound9与 `1+value` 保留局部来源关系，但不证明均匀分布、PRNG实现、种子或整场随机流位置。牌组游标消费与修补抽样消费是两种不同记录，不能把每次取牌记成一次新的随机抽样。

## 7. 成功、失败与审计边界

成功结果为 `{ok:true,schemaVersion:1,profile,policy,evidence,characters,receipt}`。`characters` 是同序的两队最终检查点，不是对来源角色对象的写入；输入的复数 `policies` 与输出的单数 `policy` 不要混淆。完整字段与收据类型见 [API](../engine/debate-turn-start-v1.md)。

`receipt.before` 与 `receipt.after` 都是 `{isTutorial:false,characters:[队0检查点,队1检查点]}`，检查点含每队输入的所有状态字段，但不含 `rawDraws`。提供式抽样是本次求值请求，不是角色状态。`receipt.teamOrder=[0,1]`，`receipt.teams` 是对应顺序的两份队收据：

- `teamIndex`、`before`、`after`：队下标和完整角色前后检查点。
- `playedCardReset`：原值和固定 `after:-1`。
- `rethinkQuota`：`before`、`after`、`crumbledApplied`、`calmApplied` 与 `reason`。原因分别为 `crumbled-and-positive-calm`、`crumbled`、`positive-calm` 或 `preserved`。即使旧额度已经为true，条件为真仍记相应Applied，不能以数值未变冒充未触发。
- `fill`：既有补牌核的完整原样收据，包括其局部抽样索引。`postFillHand`、`preSortHand`、`topicCardCountAfterFill` 与最终有效手牌表示不同阶段，不合并为一个模糊的“补牌后状态”。
- `bold`：`eligible`、`topicCardCount`、固定 `countSource:'final-post-repair-active-prefix'`、`angerTimerBefore`、`angerTimerAfter`、`resetApplied` 与 `reason`。仅正timer刚胆实际统计后，`topicCardCount` 才为数值；未进入来源刚胆门控时为null，而不是0。
- `crumbledClear`：原标记与固定 `after:false`。
- `providedRawDraws`、`consumedDraws`、`drawCount`：本队提供值、实际消费值和0或1的消费数。

刚胆原因按门控顺序为：timer0时 `timer-zero`；正timer非刚胆时 `personality-not-bold`；正timer刚胆最终有普通牌时 `topic-cards-remain`；没有普通牌且执行清零时 `no-topic-cards-reset`。前两种原因不扫描普通牌，`resetApplied=false`。timer0且非刚胆时不会优先记成非刚胆。

`receipt.consumedDraws` 是独立的全局数组，每项为 `{flatDrawIndex,teamIndex,localDrawIndex:0,draw:{role,bound,value}}`；它不改写 `fill` 内的局部 `drawIndex:0`。`receipt.drawCount` 为0、1或2，`receipt.externalRngConsumed=0`。例如两队都修补时，全局索引为0和1，而两个嵌套修补收据的局部索引仍各为0。

失败严格只返回 `{ok:false,reason}`，不含部分成功队、候选手牌、游标、timer、已消费值或可提交的半收据。严格校验是工程边界，不是对原C#在坏输入上会如何执行的承诺。错误全集、校验先后与碰撞时的精确分类以API为准；本页纸面例子不另建错误优先级。

输入不被修改或冻结，成功与失败输出均为分离且递归冻结的数据。没有隐含状态续接：后续调用需要由调用者显式提供其选择的检查点，既不自动保存牌组游标，也不把一次返回直接接入旧会话。

### 7.1 数据安全是工程准入，不是游戏规则

仅接纳可安全分离的严格普通数据，不执行getter、Proxy、函数或调用者提供的随机回调。非整数、不安全整数、负零、NaN与Infinity不通过数字安全检查；字符串和boolean不能冒充牌码、游标、容量或计时器。稀疏数组、自定义附加字段、循环引用、symbol、隐藏或访问器字段、非支持原型以及预算超限都不以“尽量修复”接纳。

组合入口要求可信Node运行时通过 `process.getBuiltinModule('node:util').types.isProxy` 检测Proxy；缺少能力时fail closed，不能退回执行不可信访问器的路径。全局上限为2048个值节点、root depth 0至12、单数组32项及32768 canonical UTF-8字节，另累计键与字符串预算；两队、七槽、18项牌组与每队0..1份draw的语义限制更窄。重复但无环的引用被独立分离并分别计入预算。

该组合预算不取代原补牌核自身的独立安全预算。安全检查细节和完整错误分类见API与政策；这些保护不意味着任意宿主环境均被支持，也不构成原生游戏行为证明。

## 8. 手工成功案例：全部未运行

以下均为人工纸面期望，不是执行回执、运行断言或测试通过记录。每个案例都假定完整schema、profile、政策与未列出的另一队满足API；简写 `draw4` 表示一份合法role、bound9、value4记录，不是实际输入格式。所有手牌数组均为七个物理槽。

### 8.1 两队完整顺序的纸面对照

队0给定：calm、timer2、容量4、手牌 `[14,12,-1,14,7,-1,0]`、已出牌9、旧额度false、旧崩坏false、游标5，牌组为 `[1,2,3,4,5,10,6,7,8,9,10,11,12,13,14,1,2,3]`，修补值4。

队1给定：bold、timer3、容量4、手牌 `[-1,14,10,12,9,0,-1]`、已出牌10、旧额度false、旧崩坏true、游标18，完整牌组同上述18项，但不会访问，修补记录为空。

先完整处理队0：已出牌变−1；正timer冷静恢复额度；0槽14覆写0；物理2从本队牌组索引5取得话术10，游标变6；填后无普通牌，修补原物理2为5并排序。最终七槽为 `[0,5,12,14,7,-1,0]`，timer仍2、额度true、崩坏false。尾槽7并未影响修补，0槽旧牌14也不被保留或放回牌组。

然后完整处理队1：已出牌变−1；旧崩坏恢复额度；0槽−1覆写0；无空位，所以游标仍18、无修补；有效前缀排序为 `[0,10,12,14]`，最终有效普通牌数0，timer3变0；最后清除崩坏。最终七槽为 `[0,10,12,14,9,0,-1]`，额度true、崩坏false。尾槽9不能阻止退怒。全局仅消费队0的那一份修补值。

这个例子中队0补牌收据的修补前普通牌数是0，但修补后的有效手牌已有5；不可用修补前0解释其他性格的退怒逻辑。

## 9. 手工拒绝案例：不是运行断言

下列每项单独改变一个原本合格的双队输入，预期整个调用失败而非仅跳过一队；具体错误先后见API。

- `isTutorial:true`：拒绝为 `unsupported-tutorial`，不能保留教程手牌而执行其余非教程组合。
- 只有一队、三队、稀疏队数组、缺少任一必需字段、未知字段、错profile、政策不完整或政策内容不同：不靠默认值接纳。
- `hand`只有4项或超过7项、有效可出槽为0、任一物理槽超出−1..14：拒绝。不能把有效0改为空位，也不能因尾槽当前不激活就容许15。
- 物理0槽为14或−1、非激活尾槽为0都不属于上述拒绝；它们分别是会被覆写的保留槽输入和合法保留尾槽，不能错误收窄准入域。
- timer为−1或5、容量为3或8、未知性格、`playedCard=15`或额度／崩坏不是boolean：拒绝，不clamp、不转换。
- 牌组不足或超过18项，未读取到的位置含非法牌码，或游标不在0..18：拒绝，不截断或补齐牌组。
- 某队cursor18且有效区还有空位，或cursor17但还需填两个空位：`unsupported-deck-regeneration`。即使保留普通牌足以跳过修补也不能避免取牌耗尽。
- 队0可以成功而队1耗尽：整个结果仍仅是失败原因，不发布队0更新。反向情形同样不能跳过队0去处理队1。
- 填后无普通牌且有新增槽却提供空修补数组：`missing-raw-draw`。不能将“没给随机值”当成“跳过修补后刚胆退怒”。
- 满手全话术、保留普通牌或新取普通牌时额外给一份修补值：`unexpected-raw-draw`。不存在“先消费再丢弃”或给另一队借用。
- 错role、错bound、value−1或9、两份本队draw，或把draw给了错误的队：不以最接近值、首份值或另一队记录补救。
- 数字为小数、负零、NaN、Infinity、字符串或boolean，恶意getter／Proxy、循环、稀疏或附加字段数组、不支持的运行时及安全预算超限：按严格数据边界拒绝，不执行调用者代码探测内容。

“合法满话术刚胆的timer变0”是成功分支；“空位需要牌组再生成或缺少修补值”是失败分支，二者不能混淆。失败无部分收据并不宣称原C#也有相同事务回滚机制，这是新组合核的工程保证。
