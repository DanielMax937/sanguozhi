# T09 one-support action: unified owner v3

## Explicit initial facts and command
The optional final creator argument is `supportConfig`:

```
{profile:'inferred-single-support-reaction-core-v1',
 relations:[{supporterId,attackerId,
  relationCase:'spouse'|'sworn'|'supporter-likes-attacker'|'parent-child'|'siblings'}]}
```

The profile requires the existing distinct-owner encounter and PK current facts. Its 1..32 fixed directed pairs must be unique, distinct actor IDs already present in the one field roster, and same-owner. They describe the existing synthetic single-leader units; they are not statements about real historical family ties. `supporter-likes-attacker` is directional from supporter to attacker. No reverse implication, overlapping-case priority or relationship creation command is provided. Missing capability preserves old defaults and saved-root shape.

Public `AttackWithSupport {actorId,targetId,supporterId,draws,foodRaidDraw?}` supplies no relationship, panel, troop snapshot, skill or technology override. The root selects exactly the configured pair; actor, supporter and target must be distinct. Current home participants additionally pass the sole city/travel availability, away and reservation gates. Enemy participants have no implicit home-city allocation or travel identity. Field and actual combat qualification verify current deployed role, normal condition, unused action, owner opposition, ordinary equipment, actual availability and adjacency to the same target. Unknown/unsupported active skills or techniques are not cleared to bypass old gates.

## One actual combat and unique state
The private field OuterStep carries the selected support policy alongside one ordinary normal-melee Attack. Only the root's full replay proves the immutable relationship and current home-role provenance; public generic Field commands cannot inject that private policy. The actual single-support projector executes the main physical attack, its existing target reaction and at most one support attempt in **one** actual resolve. It does not restart another battle to reset acted, create shadow troop balances, or copy a second standalone combat ledger into the world.

The evidence supports relation occurrence rates 50/50/30/20/20 for the respective limited cases, not support damage multipliers. The explicitly named compatibility policy performs support after the main response, consumes supporter action on a failed relation roll too, and uses half of the actual current physical core (floored). Support has no second counterattack, response fire or recursive support. No extra AP or strategy energy is charged in this ordinary-physical profile. These scheduling and half-damage decisions are stated inference, not claims of a recovered native support caller. Actual skill/tech modifiers, shields, panels and existing arithmetic remain in the core; an undefined spear-tech1 support side effect is explicitly rejected rather than silently removed.

There is one stage tape, with dedicated `support.0.*` draws after the main stages. The whole actual tape must be consumed exactly; a relation failure still has its one draw/action consequence. No separate RNG/history or repeat-free attempt is added.

## Food request, terminal guard, replay and atomicity
The root snapshots the same current food owner **before** the attack. Only the actual main attack's pre-support positive-hit food-raid request can consume `foodRaidDraw`; support damage cannot turn a blocked main hit into a new food request. An absent request with an extra draw or a request without its required draw rejects the whole action. If present, the one G food transaction is evaluated from the captured pre-attack context and committed together with all combat changes. No second base damage or support food request is produced.

Any zero/terminal main, reaction or support troop result, unsupported modifier, invalid pair, eligibility failure, incomplete/extra tape, food-settlement failure or final owner/budget invariant failure leaves main actor, supporter, target, food and acted states unchanged. Neither clamp-to-one nor partial success is allowed. One world command occupies one private field step and the existing outer history slot. The immutable config and exact action/draws are saved in the same genesis+journal root and fully reconstructed on load; independently uploaded field snapshots never establish owner provenance.

The T07 site-strike batch remains its predecessor and is not reimplemented here. T09 does not add real-person relationships, capture/death, rewards, Closing, P078, unlimited support scanning or autonomous combat AI. Original native support damage caller, combined relationship priority and version-specific details remain evidence gaps even though this finite named consumer is implemented.
