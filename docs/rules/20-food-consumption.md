# E5 兵粮消耗

更新：2026-10-03。主目标版本：PC-PK1.1。

## 1. 旬级调度

原函数：

```text
0059BF40 每旬城市港关和部队耗粮
```

每旬顺序至少包含：

1. 遍历87个城市/港/关；
2. 对有粮据点计算并扣除驻屯耗粮；
3. 遍历地图部队；
4. 对有粮部队计算并扣除部队耗粮；
5. 若本旬扣粮后恰好变成0，则加入提示/消息列表。

如果进入本旬时兵粮已经是0，`0059BF40` 会直接跳过“计算并扣粮”函数；粮尽导致的后续逃兵不在 `0049D200/0049D2E0` 里完成。

## 2. 城市 / 港 / 关驻屯耗粮

原函数：

```text
0049D200 计算城市港关兵粮支出
```

未着火时：

```text
raw = garrisonTroops × 0.025
```

即常见整数语义：

```text
驻屯基础耗粮 ≈ 兵力 / 40 / 旬
```

结果通过 `00707A74 ConvertFloatToInteger` 整数化；若兵力>0而结果<=0，强制最低耗粮1。

因此“驻屯 /40”现在是 PC-PK1.1 原函数确认，不再只是 Wiki 经验值。

## 3. 港 / 关 + 屯田：直接0耗粮

`0059BFBA～0059BFD9` 只对设施类型1/2，即港、关，检查特技：

```text
0x4E = 屯田
```

如果港/关内存在有效屯田武将，旬级 caller **直接跳过整个耗粮函数**。

所以：

```text
港 / 关 + 屯田
=> 驻屯耗粮 = 0
```

城市不走这条屯田免粮分支。

## 4. 野外战斗部队基础耗粮

原函数：

```text
0049D2E0 计算部队兵粮支出
```

战斗部队先根据同势力防御设施确定一个耗粮倍率，再统一乘：

```text
troopStrength × multiplier × 0.05
```

### 4.1 无防御设施

```text
multiplier = 2.0
=> 兵力 × 0.10
=> 兵力 / 10
```

所以：

```text
普通野外战斗部队 = 兵力 / 10 / 旬
```

### 4.2 阵 / 砦 / 城塞：使用原 float32 常量

P0-12 专项见 [47-food-overlap-starvation-exactness.md](47-food-overlap-starvation-exactness.md)。

PC-PK1.1 原指令直接写入以下 float32：

| 环境 | bit pattern | multiplier | 10000兵 |
|---|---|---:|---:|
| 无 | `0x40000000` | 2.0 | 1000 |
| 阵 | `0x3FD55555` | 1.6666666269302368 | 833 |
| 砦 | `0x3FAAAAAB` | 1.3333333730697632 | 666 |
| 城塞 | `0x3F800000` | 1.0 | 500 |

公共系数：

```text
0x3D4CCCCD
= 0.05000000074505806f
```

所以不要把阵/砦常量重写成数学上的精确 `5/3` / `4/3`。

一个重要边界：

```text
18000兵：
无     1800
阵     1499
砦     1200
城塞   900
```

阵之所以是1499而不是1500，是原 float32 常量乘算后 raw 略低于1500，再由 `00707A74 = _ftol2` 截断。

日文攻略常写15%/30%/50%，属于近似描述；PC fidelity 使用原 bit pattern。

### 4.3 重叠防御设施：确认不叠加，winner仍open

原函数：

```text
0049D2E0
→ 0049D180(troop)
→ 返回一个设施 type
→ 只进入 阵 / 砦 / 城塞 / 无 中一个 multiplier 分支
```

所以：

- 多个范围重叠不会相乘；
- 不会把节粮百分比相加；
- 同级多个设施不会重复增强。

这一层已经 source-level exact。

但 `0049D180` 完整 body 未公开，因此不同等级重叠时到底：

- 城塞优先；
- 最近优先；
- facility ID 顺序；
- 其他遍历优先；

仍 open。

兼容引擎如果必须闭环，可暂用：

```text
城塞 > 砦 > 阵
```

但必须标 `provisional-engine-rule`，不能当原版结论。

## 5. 输送队：兵力 / 20，且不吃阵砦城塞减粮

`TroopType=1` 时源码直接：

```text
multiplier = 1.0
```

并跳过防御设施判断。

所以：

```text
输送队耗粮
= 兵力 × 1.0 × 0.05
= 兵力 / 20 / 旬
```

而且：

```text
运输队在阵/砦/城塞范围内
=> 不获得上述减粮倍率
```

这比简单写“运输队是普通部队一半”更精确。

## 6. 着火会额外烧兵粮

### 6.1 野外部队

若部队着火，`0049D2E0` 额外计算：

```text
fireFood =
  currentFood
  × (6 - troopPolitics × 0.05)
  × 0.01
```

其中 `troopPolitics` 是 E2 已合成的部队政治。

正常政治0～100时：

```text
政治0   => 当前存粮 × 6%
政治100 => 当前存粮 × 1%
```

最终旬耗粮：

```text
normalTroopConsumption + fireFood
```

运输队同样会进入这个着火附加耗粮分支。

### 6.2 城市 / 港 / 关

着火据点公式完全同构，但使用太守政治：

```text
fireFood =
  currentFood
  × (6 - prefectPolitics × 0.05)
  × 0.01
```

无太守按政治0处理，即当前存粮额外约6%。

然后再加驻屯兵力的 `兵力×0.025`。

## 7. 整数化与最低1

据点和部队两个支出函数最终都调用：

```text
00707A74 ConvertFloatToInteger
```

若：

```text
兵力 > 0
且整数化结果 <= 0
```

则支出强制为1。

P0-10 已确认 `00707A74` 是 MSVC `_ftol2`，语义为向0截断。耗粮 raw 在正常规则域为正，因此这里可以直接写成语言级 `floor`。仍需单独保留的是防御设施浮点常量 bit pattern 与 x87 中间精度，而不是最终转换方式。

## 8. 粮尽与逃兵：P0-12 进一步收紧

`0059BF40` 对进入本旬时已经0粮的对象直接跳过：

```text
据点：
0059BFB6 test food
0059BFB8 jle next

部队：
0059C06A cmp [troop+20],0
0059C06D jna next
```

若本旬从正粮扣到0，函数只把对象加入粮尽提示列表；直到函数结尾都没有扣 troop strength。

因此可以确认：

```text
0059BF40 = 耗粮 + 粮尽提示
粮尽掉兵 = 另一条独立每回合处理链
```

官方手册和长期实机都确认0粮会导致士兵下降，但当前公开 PC-PK1.1 资料仍没有恢复野外 troop starvation/desertion 的函数地址或闭式。

### 8.1 00599AA0 不是野外部队粮尽函数

```text
00599AA0 ReducePopForStarvedBesiegedSP
```

是：

```text
兵临城下 + 据点断粮
→ 据点人口衰减
```

不能拿来解释野外部队掉兵。

### 8.2 旧 0.76 证据降级

旧规则：

```text
remaining ≈ A × 0.76^N
```

回查后没有找到可靠受控实验、原地址或样本表支持精确0.76。因此从 `empirical-high` 降为：

```text
legacy-compatibility-only
provenance-unresolved
```

严格 fidelity 不再默认使用0.76。

如果旧模拟需要保持历史兼容，可以保留单独 profile：

```text
legacyRetentionPerTurn = 0.76
```

但它不能进入原版规则层。

## 9. 旧规则的纠错

现在确认：

- “战斗部队 /10”——正确，升级为源码确认；
- “输送队 /20”——正确，升级为源码确认；
- “据点驻屯 /40”——正确，升级为源码确认；
- “港关+屯田=0”——正确，且仅港/关适用；
- “阵/砦/城塞减粮15%/30%/50%”——前两项不是 fidelity 精确值，应改为源码常量对应约16.67%/33.33%/50%；
- “运输队在防御设施范围也减粮”——错误，源码直接跳过该分支；
- “着火只掉兵，不额外烧粮”——错误，部队与据点都有政治相关的额外存粮损失；
- “粮尽0.76是高置信实测”——当前也不能成立；P0-12 已降为 provenance-unresolved 的 legacy compatibility 常量。

## 11. 仍 open

1. `0049D180` 完整函数体，以及不同等级防御设施重叠时的 winner priority。
2. 野外粮尽部队掉兵的 PC-PK1.1 原函数地址与闭式 / RNG。
3. 战斗队与输送队的粮尽掉兵是否共用同一规则。
4. 首个粮尽旬与持续粮尽旬是否有区别。
5. Vanilla / 主机版防御设施 float32 常量和 starvation 路径是否一致。

已不再 open：

- 防御设施倍率的 float32 bit pattern；
- 最终正值整数化方式（P0-10 `_ftol2`）；
- 重叠效果是否叠乘（明确不叠乘）。
