# 时间、回合、难度与剧本

## 1. 时间单位与周期触发

- `[COMMON][confirmed]` 1 回合（旬）= 10 日；每月 3 旬：1日、11日、21日。
- `[PC-PK1.1][reverse-engineered]` 普通金收入在每月 1 日结算。
- `[PC-PK1.1][reverse-engineered]` 普通粮收入在 1/4/7/10 月 1 日结算。
- `[PC-PK1.1][reverse-engineered]` 城市、港关、部队兵粮消耗每旬结算一次。

### 征税 / 征收实际改变收入 tick

原函数并不是简单把月/季收入最后乘 1.5。

征税：

```ts
// 正常月收入 = M
月初: floor(M / 2)
11日: floor(M / 2)
21日: floor(M / 2)
```

因此一个完整月约为普通月收入的 150%，但整数取整按每次 tick 分别发生。

征收：

```ts
// 正常季度粮收入 = Q
季度首月: floor(Q / 2)
季度第二月: floor(Q / 2)
季度第三月: floor(Q / 2)
```

因此一个完整季度约为普通季度粮收入的 150%。非季初因征收触发的收粮不会重复叠加米道等只在正常季度收入分支生效的效果。

来源：
- 311MemoryResearch `Func-收支01-每旬收钱.txt`
- 311MemoryResearch `Func-收支03-每月钱粮兵装收支.txt`

## 2. 原作旬/月结算顺序

`[PC-PK1.1][reverse-engineered-partial]`

原公开逆向已经恢复 `00590C30 MonthlyAction`，所以**月初内部顺序**不再使用旧的“推荐顺序”冒充原作事实。

当前已确认：

```text
月初判定
↓
俘虏月份 / 禁止仕官月份计数
↓
年龄 / 死亡相关处理
↓
一个尚未命名的月度处理
↓
俘虏逃跑
↓
丰作状态处理
↓
00590490 MonthlyIncomeAndExpend
    ├─ 城市金收入
    ├─ 城市粮收入
    ├─ 季初治安下降
    ├─ 港关钱粮收入
    ├─ 俘虏费用
    ├─ 武将俸禄
    ├─ 资金不足后果
    └─ 自动特产兵装生产
↓
皇帝 / 铜雀台 / 玉玺技巧点
↓
在野武将随机移动 / 自动出仕
↓
若干月度处理
↓
季初武将忠诚下降
↓
后续月度/季度处理
```

重要边界：

- 月初年龄/死亡、俘虏逃跑等部分人员处理发生在钱粮收入之前。
- 季初城市先计算本次钱粮收入，再调用自然治安下降函数。
- 月度经济内部先收入，再按据点先扣俘虏维护（50金/人），再汇总现役武将官职俸禄；俸禄足额则直接扣除，付不起则转 `0058D5E0 -> 0058C190` 欠薪忠诚处理。俸禄是每月，不是季度。
- 自动特产兵装生产发生在月度收支之后。

每旬已确认存在的独立处理函数包括：

- `00599600` 每旬征税额外收钱
- `00599710` 设施耐久恢复
- `00599AA0` 兵临城下逃兵
- `00599B90` 部队异常状态
- `00599CF0` 研究/任务等计数器推进
- `0059BF40` 城市/港关/部队兵粮消耗

但公开资料尚未取得 `00580100 MainLoop` 的完整函数体，因此这些**每旬函数彼此的全局先后**仍为 open；不要再用地址大小推断调用顺序。

## 3. 势力行动顺序

`[COMMON][empirical-high]`

行动顺序会动态变化，不固定为剧本势力列表顺序。老玩家长期实测支持以下前三层：

1. 爵位较低的势力先行动；
2. 爵位相同时，支配都市较少的势力先行动；
3. 前两项相同时，所属武将较少的势力先行动。

升爵位、增减都市或武将后，下一旬可能发生顺序翻转，从而出现相邻两旬连续行动/连续被行动。

### 未确认的最终 tie-break

目前没有原作证据支持“势力 ID 是最后排序键”。后期整理资料存在“港关数 → 完全相同则随机”的说法，但尚未取得原 comparator 函数体。

因此 fidelity 引擎不要把 `forceId` 伪装成原作规则。若为了可运行必须 tie-break，可临时使用**每旬基于 Scenario RNG 的稳定随机键**，并标记 `provisional-engine-rule`。

源码侧已确认存在：

- `00436740 GetNobilityOfForce`
- `004C3BE0 GetForceCityNum`
- `004C3C50 GetForcePersonNum`
- `07834530 CurrentActionForceID`

但尚未找到把这些键串起来的原排序函数。

## 4. 难度

运行时：

```text
scenario + 0x20 = DifficultyLevel
0 = 初级
1 = 上级
2 = 超级
```

### 已反汇编确认的主要差异

| 系统 | 初级 | 上级 | 超级 |
|---|---:|---:|---:|
| 城市金/粮收入 | ×1.25 | ×1.00 | 玩家×0.75；AI×1.25 |
| AI征兵 | ×1 | ×1 | ×2 |
| AI普通枪/戟/弩/马生产 | ×1 | ×1 | ×2 |
| 玩家部队主要伤害链 | ×1 | ×1 | ×0.75 |
| 玩家所属设施攻击伤害 | ×1 | ×1 | ×0.8 |
| AI出兵策略 | 读取 difficulty | 读取 difficulty | 读取 difficulty |

收入难度倍率发生在治安修正之前。

超级难度的 AI 初始兵力/金粮/兵装倍增已有长期稳定实测，但完整初始化函数尚未取得，继续标 `empirical-high`，不要与上表的反汇编项混为一类。

### 战场计略

现有 `计策成功率` / `计策爆击率` 逆向函数未发现直接读取 Difficulty；超级隐藏部分成功率 UI 不等于底层概率统一乘惩罚。

### 单挑

单挑原 C++ 翻译代码还存在独立难度分支，详见 `10-duel.md`。核心包括：

- 初级玩家对 AI 普通伤害约 ×1.1，AI 对玩家约 ×0.8；
- 初级玩家斗志 ×1.2；
- 超级玩家斗志 ×0.8、AI 斗志 ×1.2；
- 上级/超级还提高 AI 对玩家部分必杀/一击必杀相关概率，并降低反向概率。

### 当前撤回的旧结论

没有找到可靠源码证明“技巧研究时间因初级/上级/超级而改变”。`00599CF0` 只负责每旬将剩余研究时间减 1；研究初始日数的难度修正仍未发现。因此不得再把“超级技巧研究时间不同”写成 confirmed。

同样，完整的季初忠诚下降函数未发现 difficulty 分支；“超级更容易掉忠”目前仅能保留为社区观察待核项。

## 5. 剧本初始化

`[PC-PK1.1][reverse-engineered-structure]`

剧本文件中的静态字段不是最终运行状态的全部来源。运行时 `struct_scenario` 本身直接保存：

```text
ScenarioNumber
StartYear / StartMonth / StartDay
EmperorID
IgnoreAge
DifficultyLevel
DieInBattleSetting
AttrChange
PortraitChange
MagicThunder
FemalPerson
Lifetime
Event
BloodTie
InterpersonalRelationship
Phrase
Character
ComeOnStage
GameTime
RandomSeed
CurrentRoundNumber
```

并在同一 Scenario 对象后连续保存城市、港关、势力、军团、1100 武将、宝物、建筑、部队和事件状态。

因此正确模型是：

```text
公共定义 / 基础人物资料
↓
选定剧本状态快照
↓
玩家开局规则选项
↓
史实/假想等转换
↓
难度相关开局资源修正
↓
日期 / 回合 / RNG state 初始化
↓
构建派生链表和事件状态
↓
进入第一旬
```

至少应区分：

```ts
PersonDefinition
ScenarioPersonState
ScenarioOptions
RuntimeScenario
```

而不是把所有字段扁平化为一份静态 JSON。

### RNG 是世界状态

`struct_scenario + 0x58 = RandomSeed`。原 RNG 已逆出为固定种子、固定递推序列，因此存档必须保存 RNG state；否则读档后的登用、计略、治安、AI 选择等随机结果无法复现。

### 默认人物层

逆向记录显示游戏加载时会读取 `Scen007.s11`（英雄集结）的武将数据作为一层默认数据源；当前尚未取得完整 loader，因此不要外推成“所有字段都由 Scen007 覆盖”。

### 仍缺

当前 repo 仍缺：

- 各主剧本完整初始状态数据；
- 超级 AI 开局资源修正的完整 loader 函数；
- 史实/假想各开局选项的逐字段转换函数；
- 所有事件初始 flag 的结构化录入。
