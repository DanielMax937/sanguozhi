## F: separate sides, actual combat, no imaginary home enemy

Optional `encounterConfig` uses the exact F/v4 contract in `inferred-field-encounter-v4.md`: home owner equals the city force; enemy owner, enemy actors, fixed troop budget, equipment/panels and supplied combat map are explicit immutable synthetic new-game facts. Each enemy initial troop amount is positive and the exact sum equals its budget. Enemy is not a home officer relabeled hostile. Its ID/owner/encounter ID cannot alias city, corps, force, episode, home officer/facility, field cell/map, transport, item, bound traveler or fixed economic facility IDs. The same field roster is the unique current position/troop/energy/action/condition owner for both sides. Enemy cannot Deploy/Return or become a city, payroll, PK, training, grant, research or travel actor. No enemy AI is installed.

`Field.command` now admits actual `Attack`, `FalseReport` and configured `Rockfall` alongside old Cast/FireCast. Attack uses the real field-combat kernel, full positive-response transaction and current action lock. Neutral unsupported skills remain explicitly rejected rather than silently erased. Current battlefield intelligence/charisma come from the live PK facts; treasure effective statistics remain a separate known follow-on consumer gap, not implicitly included here. Troop allocation output counts only home template IDs in the home field total and reports enemy initial/current troops separately. Creation budgets are initial allocations, not assertions that casualties/recruitment never change total troops.

Food-before-fire is a named composition policy, not a recovered native caller order. Any failure in damage, recovery, food, travel, date, jobs or output budget rejects the whole outer event. Zero-troop finalization remains excluded.

## G: single food ownership and real transfers

Optional exact `fieldFoodConfig`:
```
{ profile:'unified-field-food-owner-v1',
  transportPositions:[{id,cellId:null|fieldCellId}],
  enemyInitialFood:[{actorId,food}], enemyFoodBudget }
```
Every transport is listed exactly once; its fixed location is a named synthetic supply-position assumption, not implemented moving transport AI. Transport food capacity must be 500000 for this supported leaf domain. All field actors have capacity50000; home starts with zero food, resident actors retain no allocated food. Every enemy actor is listed exactly once with 0..50000 initial food and the exact sum equals the immutable enemyFoodBudget (0..400000). This is independent enemy new-game resource evidence, not home duplication, a runtime gift, or a helper-supplied balance. Field troops must fit the existing G domain ≤60000; initial validation and deployment gates reject unsupported values, never clamp. The leaf requires reciprocal adjacency; no unproved alternate geometry is invented.

With this profile Deploy requires explicit `food`, moves it from the actual city stock into that actor's allocation atomically with troop deployment/AP/action locks. Return returns all remaining actor food to the same city's capacity-limited ledger atomically with role/troops/weighted morale; no balance survives in a resident actor. `ManualSupply{transportId,actorId,requestedFood}` transfers only food between current same-owner adjacent transport and deployed field actor; the accepted amount is capped by source stock and target room, unused food stays at source. It is deliberately food-only, not a claim that gold/troop/equipment manual supply is implemented. No undocumented extra AP or transport action fee is fabricated.

FieldTick consumes the actual neutral food arithmetic plus current fire/politics from `synthetic-field-food-leaf-v1.md`. It changes food only, allows food0 and does not cause starvation troop loss/health events. Food is stored exactly once in city ledger, transport stock or field allocation; the temporary proposal contexts are not persistent ledgers. Every patch checks its before value. Initial validation uses a discarded pure proposal, not a hidden initial debit. Existing city/cargo consumption and new field consumption have disjoint account sets.

Request event ID is the deterministic internal outer-step index, fully replayed from the original outer journal; it is not the user's external command ID or cryptographic proof.
