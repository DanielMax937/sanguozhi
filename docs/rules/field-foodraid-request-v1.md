# T21 real-tech combat / externally settled food-raid request

This additive, explicit request profile preserves actual learned technique IDs in combat. It does not clear tech1 to evade `unsupported-food-raid`, does not pretend the old empty-tech neutral projection consumed researched effects, and does not write food inside the combat kernel. The default old context and its preflight rejection remain unchanged.

## Actual source and narrow kernel change
Base `field-combat-lifecycle.ts` was read at Git blob `2d540284a44384833e01ff823571b07820c1111f`. Its exact prior gate is non-strategy + spear + techniques.includes(1) → unsupported-food-raid. Technique0 is genuinely used by the normal damage calculation (training multiplier1.10; elite takes priority1.15); shields and response fire also use actual technique facts. Therefore deleting the whole list is not a valid bridge.

New optional **genesis context** `foodRaidMode:'external-positive-proposal-v1'` admits only an active `normal-melee` spear action with both techniques0 and1. Other actions involving this unsupported side effect still reject. The same actual technique array continues through the original full physical damage, shield, range, response and positive-only gates. No formula or default policy is changed. Optional context is validated, saved in genesis and replayed; absence stays absent, so default source data/receipts do not gain a silent flag. It is not a runtime bypass switch.

Only after the actual action has resolved successfully and all participants remain positive does its actual receipt include:
```
foodRaidRequest: {
 eventId: command.commandId, actorId, targetId,
 attackPanel: actualUsedPanelAtActionStart.attack,
 weapon:'spear', techniques:[actual complete technique IDs], action:'normal-melee'
},
requiresExternalFoodSettlement: true
```
No caller may supply this request. The eligibility is a named conservative finite positive-hit action contract, not a newly proven original post-hit caller; only a committed action with actual target troop loss >0 meets the conservative explicit action contract; shield-blocked or zero-damage actions produce no request. If original post-damage eligibility is later established differently, version this contract. Terminal damage or any kernel failure emits no accepted request. Counterattacks do not create a second raid. This profile neither reads nor writes food and cannot by itself claim the whole world attack is committed.

## Field / owner API
The cumulative cultivated field includes F + H (single roster, conditions, optional enemy/hazards) from the separately reviewed candidate. To opt into actual owner technique snapshots, encounterConfig additionally contains both:
`foodRaidMode:'external-positive-proposal-v1', enemyTechniqueIds:number[]`.
Enemy IDs0..35 are unique, explicit and immutable in enemy genesis; no borrowed home research or implicit enemy AI.

Private OuterStep may carry `combatTechniquesByOwner:[{ownerId,techniques}, {ownerId,techniques}]`. In this mode Attack/FalseReport require exact two distinct configured owners. Enemy list must equal its fixed genesis list; home list must be generated by the actual outer research owner from current completed techniques. The field validates consistency, not external research provenance. Public World Field actions must never accept this field. The enclosing world's sole journal regenerates it, exactly like PK facts. If actual learned techniques are present, outer owner must not select the legacy neutral-empty-tech profile. Nonempty technique snapshots without the explicit profile reject; no silent fallback empties them.

The old kernel sees the entire real lists, not just0/1. Normal Attack optionally carries exact stage tape `{stage,bound:100,value}` for actual shield/response/critical consumption; neutral absent-skill critical remains deterministic where the old kernel says so. Extra/missing/wrong-stage draws reject. FalseReport still uses its separate actual strategy stage tape. Unknown passive/skill contexts remain rejected by the existing explicit neutral skill guard, not mapped from names without evidence.

A successful field Attack receipt has `pendingFoodRaidRequest` copied from the actual combat receipt and `requiresExternalFoodSettlement:true`. Locate it by current commandId, not by scanning an earlier action. It is an obligation, not a user-provided eligibility declaration. The field holds no duplicate food balance and no acknowledged-settlement flag; only the outer owner can atomically combine it with actual food data.

## Mandatory outer atomic consumer
World must:
1. Capture the same pre-attack unique actor/target food, troop and capacity state, owners, positions and actual learned technique lists.
2. Run field Attack with its internal actual-tech snapshot. A failed field result commits nothing.
3. If this action produced the exact request, call actual G food-raid leaf with that request, the captured pre-attack stocks/troops, and the public action's independent foodRaidDraw0..10. Do not reuse physical/strategy draws. Formula/source consumption belongs to that existing G leaf (panel-scaled request, own-troop half-cap, enemy stock/receiver capacity caps), not this kernel.
4. Only after G succeeds commit both proposed field and food writes to the single outer journal. Missing G capability, missing required draw, unsupported food domain or any failure rolls back damage, counterattack, actions and food together. Draw supplied without a request also rejects.
5. Public Field may carry foodRaidDraw only in the world's typed wrapper; strip it before calling the field action parser. It must not include a fabricated request or technique list.

The kernel's local committed combat snapshot is a proposal awaiting this outer transaction, not permission to drop the food obligation. Standalone callers must not advertise full food-raid completion. The final review must include actual owner consumer; this candidate alone is not the completed world integration.

No new healer/injury/deficit effects, global authority, real ownership, P078, Closing reward, zero termination or AI are introduced. Existing positive bounds and shared action/hazard budgets remain. G may impose a smaller positive troop domain; owner must validate/reject unsupported genesis, never clamp. Static-only changes, no tests/typecheck/build/code execution or remote writes.

Cumulative prerequisites: frozen F enemy/Attack contract, H unified condition and actual FalseReport/entry/rockfall contract (including plain-entry preflight and explicit neutral learned-skill rejection), and PK current-facts bridge. These remain conditional capabilities, not claims of complete original battlefield equivalence.
